# Sovereignty assessment

_Confidential. Property of Tiger Capital AI. Written from the point of view of the institution that owns the deployment._

"Sovereign" here means five things an owner can test: **the institution holds the data, holds the keys, can stop the system, can leave it, and can prove nobody changed the record behind its back.** This page checks each against the code and says plainly what is built, what was only built and tested on a development machine, and what is still missing. Nothing here has run on a client's infrastructure yet.

## Where the work is

All of it is in the repository (`main`), committed and pushed. It has not been deployed anywhere and no client environment exists. The web image has been built from this repository and run on the development machine; the application image could not be built there because the Debian package mirror is not reachable from that environment, and the CI workflows have never run on GitHub. "Built" below means code, tests against a real PostgreSQL, and a browser suite against the real API. It does not mean proven on the client's hardware.

## Found in this audit and fixed

| Finding | Fix |
|---|---|
| A token stayed valid until its own expiry; the identity provider could issue a long-lived one and nothing here bounded it. There was no way to end a session short of disabling the person. | A maximum token age (`OIDC_MAX_TOKEN_AGE_SECONDS`, eight hours by default; tokens without an issue time are refused). Administrators can end one person's sessions or everyone's, with a recorded reason. Signing out now ends all of the person's sessions, not just the browser's copy. Migration 0018. |
| The audit chain uses an unkeyed hash. Someone with full database rights can rewrite every event and recompute the chain, and `verify` still says "intact". Shown by a test. | Signed checkpoints: the head of the chain signed with a key kept outside the database (`TIGERIS_AUDIT_ANCHOR_KEY`). Verification detects an altered checkpoint, another key, rewritten history and a chain cut short. Screens on the Audit page. |
| No emergency stop. The only way to freeze the system was to shut containers down, which also removes the ability to investigate through it. | Lockdown (migration 0019): refuses everything except the investigation and release routes, pauses scheduled fetching, audited. Screen on Administration. |
| Once Sign out really ended every session, signing straight back in could be refused for up to a second, because tokens are dated to the whole second (the browser suite caught it). | A person's own sign-out cuts at the current second, so a new sign-in works at once; an administrator's revocation cuts at the next second, so nothing issued before it survives. |
| The Sign out button never called the new "end all my sessions" route, although it was reported as doing so. | Fixed; the button now ends every session of the person. |
| Building the web image showed that nginx ignored the script that writes the web app's runtime settings ("not executable"), so a deployed container would have used the development identity-provider address and an unset CSP origin. | Renamed to the file type the entrypoint sources and given its mode in the Dockerfile; verified in a running container, including that it fails fast when a setting is missing. |
| Readiness did not mention encryption at rest or the audit signing key. | Two new checks: audit signing key (warns when absent) and storage encryption (a manual confirmation). |

## Still missing, with the solution

Ordered by how much a sovereign owner should care.

**A. The egress route.** *Built:* the API, set-up and ingest containers no longer have any route out. They sit on the internal network only and reach the outside solely through an egress proxy (`packages/core/src/egress-proxy.ts`) that opens an encrypted tunnel to exactly the host:port pairs in `EGRESS_ALLOW` and refuses everything else, plain HTTP included. A listed name that resolves to a private address is refused unless it was listed as private on purpose, so an allowed name cannot be pointed back at the institution's own network. Every decision is logged. Identity-provider keys, source fetches, a hosted model and the mail relay all go through it. A host firewall file (`deploy/egress/nftables.conf`, syntax-checked) is the second layer, and `scripts/egress-check.mjs` proves the boundary from inside the container. *Proved here:* the proxy's behaviour (listed, unlisted, wrong port, private address, plain HTTP, tunnel limit), that a Node program honours the proxy settings, that the compose file's network shape is as intended (a test reads the file), and that the check script passes against a correct proxy and fails against an open one. *Not proved here:* that Docker's network really gives the API no route out, because the container network could not be run on the development machine (no bridge networking); the firewall rules were checked for syntax but never loaded. Run `egress-check` and load the firewall file in the client's environment.

**B. Document contents.** *Built (my decision on the search question):* uploaded files and extracted page text are sealed by the application (AES-256-GCM, a fresh nonce each time, bound to the row so a sealed value cannot be moved to another document or page) before they reach the database, with a key from the secret store (`TIGERIS_DOCUMENT_KEY`) that the database never holds. Search keeps working without decrypting the library: each page stores keyed word tokens (an HMAC of every word), a search looks the query's words up by their tokens, keeps pages that contain all of them, ranks by how often they occur, and builds the snippet from the one page it decrypts. Production refuses to enable institution documents without the key, and Readiness fails until it is set.

*What I chose and why:* an in-memory index would have been simpler to explain but loses search after every restart, holds the whole text in memory and is a second place plain text lives. Dropping search would have made institution documents much less useful. The keyed word index keeps exact-word search at the cost of the leaks below.

*What this does not hide:* a database administrator can see that two pages share a word and how often it occurs, and could confirm a guess about a common word by frequency analysis. They cannot read the words. The title, file name, page counts, character counts and a SHA-256 of each page (kept for integrity) are not sealed, so a person who can already guess a whole page can confirm it. Search is whole-word only: no stemming, no phrase search, no partial words. *Key handling:* losing the key loses the documents, so back it up separately from the database. A replaced key stays readable through `TIGERIS_DOCUMENT_KEY_PREVIOUS`; re-sealing old documents under a new key is not built, because the stored rows are immutable by design, so old keys must be kept as long as the documents are. Documents stored before the key was set stay as they were and are still readable and searchable.

**C. A checkpoint is only useful if it lands somewhere the database administrator cannot change.** *Built:* a scheduler (`TIGERIS_AUDIT_CHECKPOINT_DIR`, every 24 hours by default) writes signed, read-only checkpoint files atomically, records each save in the audit trail only after the file exists, and alerts administrators and auditors when none has been saved for twice the interval. *Still the client's:* the folder must be a write-once or remote mount the database administrator has no rights on, the signing key must be out of that person's reach, and a named person must check the newest file now and then. A folder on the same server proves nothing.

**D. Leaving in an open format.** *Built:* `pnpm retention export <new folder>` writes every institution table as newline-delimited JSON with a manifest of hashes and the audit chain status, all read at one instant; `pnpm retention verify-export <folder>` checks it with nothing but the files. It is itself recorded in the audit trail. Measured only on the development database (43 tables, 54,000 rows); not tried at production size, and restoring from it into another system is a documented format, not a tool.

**E. Sign-in depends on one outside system.** *Built:* emergency sign-in. `pnpm identity break-glass init` makes an Ed25519 key and splits its private half into two shares for two different custodians; the application knows only the public half (`TIGERIS_BREAKGLASS_PUBLIC_KEY`). `break-glass issue` needs both shares, names an existing active administrator, must give a reason, and lasts at most four hours. The token is accepted as a sign-in for that person, is marked as emergency access on every screen, is audited on first use with its reason, and raises an alert to administrators and auditors for a day. It obeys ended sessions and the emergency stop. *Not built:* the custodians, the sealed storage of the shares, and the drill. Those are the institution's to arrange, and the drill is on the acceptance list. A person holding both shares can sign in as any administrator: the two custodians must not be the people the break-glass route is meant to check.

**F. Supply chain.** *Built:* every base image is pinned by digest (Dockerfile, database image, scanner image), and `scripts/release.mjs` refuses a release that pulls any image by tag alone or comes from a tree with uncommitted changes; a signed release manifest (commit, lock file, bill of materials, migrations, base images, built image ids, offline bundle hash) with `scripts/verify-release.mjs` to check it with only the public key; a secret scan in `pnpm check` that fails on private keys, tokens and connection strings; the bill of materials now includes the operating-system packages of the web image and the Node base image (an actual list from images pulled here); a manual `release.yml` workflow that builds, lists packages and signs. *Not done:* the application image's own package list (it adds the PDF and OCR tools) because the Debian package mirror is not reachable from the development environment; image signing with a registry (cosign) is described, not built; `release.yml` and the CI `images` job have never run on GitHub; the secret scan is pattern-based and will miss a secret that looks like prose. The signing key is the signer's to hold.

**G. Granting authority.** *Built (decided with you):* giving anyone `administrator` or `approver` becomes a request that a different administrator must approve. The person who asks cannot approve, and nobody can approve a role for themselves; the asker may withdraw. Other roles apply at once, as does taking any role away. Set-up and the identity command (`pnpm identity add`) still apply everything, which is the break-glass route for the first administrators and needs access to the server. *Not built:* nobody is alerted that a request is waiting, so administrators must look at the Administration page; and with only one active administrator no one can approve, so keep at least two (set-up already requires it).

**H. Vendor access.** *Built:* access that ends by itself (a person can be created with an expiry; the API refuses them afterwards, hides them from pickers and sends them no notices; extending it needs a reason and is audited), and a per-person activity report an auditor can read to review what a temporary person did. *Written:* [VENDOR-ACCESS.md](VENDOR-ACCESS.md), a policy for the institution to adopt or change. It is a proposal: nothing about it binds anyone until the institution approves it.

**I. Lockdown is a software stop.** It refuses requests but the process, the database and the scheduler containers keep running. *Now paired with:* the egress proxy, which can be stopped on its own (`docker compose stop egress-proxy`) to cut every outbound connection at once, and the host firewall file. The runbook says to stop the proxy during an incident whose cause is not understood.

**J. Proof in the real environment.** *Built:* an acceptance run (`scripts/acceptance.mjs`) the institution executes against its own deployment (TLS and headers, a real multi-factor sign-in, readiness, backup monitoring, the audit chain and a checkpoint, mail, the real scanner), a list of manual items that each need an evidence file recorded by hash, a signed report that says ACCEPTED only when nothing failed and nothing is open, and penetration-test scope and rules in [ACCEPTANCE.md](ACCEPTANCE.md). *Also done:* the web image was built from this repository and run here (TLS 1.2 and 1.3 only, security headers, redirect, runs as an unprivileged user), which found and fixed a real defect (VERIFICATION-REPORT item 26). *Still open, and only the institution can close it:* a real identity provider, a real mail relay, scanner signatures, the official PostgreSQL image and the restore drill, the application image build, the egress and firewall proof, and an independent penetration test. A report with those items marked OPEN says so.
